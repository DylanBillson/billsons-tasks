# Billson's Tasks

Billson's Tasks is a self-hosted workplace task-management platform designed
for organisations that need structured work management across multiple teams
or companies.

Work is organised into companies, sections, lists and tasks, with explicit
membership controls, task assignments, comments, history, audit logging and
multi-user collaboration.

Designed as part of the Billson Stack, Billson's Tasks prioritises
self-hosting, clear permissions, operational simplicity, data ownership and
server-side security.

---

## Features

### Companies and Organisational Isolation

A single Billson's Tasks installation can host multiple companies while
keeping their data isolated.

The core hierarchy is:

```text
Company
└── Section
    └── List
        └── Task
```

Companies act as the highest organisational boundary.

Standard users cannot discover or access companies they do not belong to.

---

### Sections and Task Boards

Sections provide the primary working areas within a company.

A section can represent:

* A project
* A department
* A workstream
* An operational area
* A topic
* Any other logical grouping of work

Each section contains ordered task lists.

Lists are flexible and have no fixed semantic meaning.

Example:

```text
Website
├── Backlog
├── Planning
├── In Progress
├── Review
└── Completed
```

Task completion is independent of list placement.

Moving a task into a list called `Completed` does not automatically complete
the task.

---

### Drag-and-Drop Task Management

Section boards support drag-and-drop organisation using SortableJS.

Supported interactions include:

* Reordering tasks within a list
* Moving tasks between lists
* Reordering lists
* Drag handles
* Animated drag previews
* Drop-target highlighting
* Insertion indicators
* Horizontal and vertical auto-scrolling

Drag-and-drop operations are validated by the server and use optimistic
concurrency protection to avoid overwriting changes made by another user.

---

### Tasks

Tasks support:

* Title
* Description
* Due date and time
* Ordered list position
* Completion state
* Multiple assignees
* Comments
* Task history
* Soft deletion
* Restoration
* Permanent deletion by administrators

Tasks can be:

* Created
* Edited
* Reordered
* Moved between lists
* Completed
* Reopened
* Deleted
* Restored

Deleted tasks remain available to administrators until permanently removed.

---

### Multiple Assignees

Tasks may be assigned to multiple users.

Assignments represent responsibility rather than ownership.

Users may only be assigned when they have access to the relevant section.

The task detail page provides:

* Current assignees
* Assignment management
* Available-user selection
* Removal controls

Assignment changes are included in task history.

---

### Comments

Users with task access may discuss work directly on a task.

Comments support:

* Author attribution
* Creation timestamps
* Soft deletion
* Permission-controlled deletion
* Newest-first display

Deleted comments remain represented historically without exposing their
original content.

---

### Task History

Each task maintains a chronological history of significant activity.

History may include:

* Task creation
* Task edits
* Completion
* Reopening
* Movement
* Assignment changes
* Other significant task actions

History is generated by the application and cannot be edited or reordered by
users.

---

### My Tasks

The My Tasks view provides a personal overview of work assigned to the
authenticated user.

Tasks can be filtered by:

* State
* Company
* Section
* Search text

Supported states include:

* Open
* Completed
* Overdue
* All

Only tasks the current user is authorised to access are returned.

---

### Live Multi-User Updates

Billson's Tasks supports polling-based multi-user collaboration.

Section boards and task detail pages periodically check lightweight revision
endpoints to determine whether another user has changed the current resource.

Supported behaviour includes:

* Section board change detection
* Task detail change detection
* Comment change detection
* Assignment change detection
* Task history change detection
* Drag-and-drop conflict detection
* Permission-aware polling
* Automatic pause while tabs are hidden
* Automatic pause during drag operations
* Deferred refresh while users are editing forms
* Offline and error handling

Live updates use ordinary HTTP polling rather than persistent WebSocket
connections.

This keeps deployment simple and requires no message broker or additional
real-time infrastructure.

See:

```text
docs/live_updates.md
```

for the full design.

---

### User Management

Administrators can manage the complete user lifecycle.

Supported operations include:

* Create users
* Edit users
* Activate users
* Deactivate users
* Reset passwords
* Anonymise users

Anonymisation is permanent and preserves historical relationships where
required for audit and task history.

Administrators cannot deactivate or anonymise themselves.

---

### Company Membership

Companies support two membership roles:

```text
Manager
Employee
```

Employees may:

* View companies they belong to
* Access sections they are assigned to
* Work with tasks in those sections

Managers additionally may:

* Create sections
* Manage company membership
* Add company members
* Remove company members
* Change company roles

Company management does not automatically grant access to every section.

Section access remains explicit.

---

### Section Membership

Section membership determines access to day-to-day work.

A standard user normally requires:

```text
Company Membership
        +
Section Membership
```

before accessing a section or its tasks.

Administrators may bypass normal membership restrictions.

---

### Administration

Billson's Tasks includes a dedicated administration interface.

Administrative areas include:

* User management
* Company management
* Archived companies
* Archived sections
* Deleted tasks
* Audit log

Administrative functionality is isolated from normal task-management
operations.

---

### Audit Logging

Significant application and administrative actions are recorded in an
immutable audit log.

Audit information may include:

* Acting user
* Event type
* Timestamp
* Related entity
* Human-readable details
* Supporting metadata

Examples include:

* Authentication activity
* User lifecycle changes
* Company administration
* Section administration
* Task recovery
* Feedback submission

Audit access is restricted to administrators.

See:

```text
docs/audit_logging.md
```

for more information.

---

### Feedback

Authenticated users may submit feedback from within the application.

Feedback:

* Is sent by email
* Is not stored as application content
* Is protected by CSRF validation
* Generates an audit event
* Cannot be submitted anonymously

---

### Timezone Support

Application timestamps are stored in UTC.

Display values are converted using the configured application timezone.

Example:

```env
DEFAULT_TIMEZONE=Europe/London
```

This keeps database timestamps consistent while presenting dates and times
appropriately to users.

## Permission Model

Billson's Tasks uses a layered permission model.

```text
Authentication
        │
        ▼
User State
        │
        ▼
Global Role
        │
        ▼
Company Membership
        │
        ▼
Section Membership
        │
        ▼
Entity Permission
        │
        ▼
Business Rules
```

Permission enforcement is always server-side.

Client-side controls, hidden navigation items and JavaScript behaviour are
never treated as security boundaries.

Live-update requests, drag-and-drop operations, forms and ordinary page
requests all use the same underlying permission services.

See:

```text
docs/permissions.md
```

for the complete permission model.

## Roles

### Global Roles

Billson's Tasks currently has two global roles:

```text
Administrator
User
```

Administrators have application-wide administrative access.

Standard users receive access through company and section memberships.

### Company Roles

Companies have two membership roles:

```text
Manager
Employee
```

Company roles apply only within the relevant company.

## Security

Billson's Tasks includes:

* Server-side permission enforcement
* Explicit company isolation
* Explicit section isolation
* Secure session authentication
* CSRF protection
* Password hashing
* Soft deletion for recoverable records
* Immutable audit records
* Optimistic concurrency protection
* Permission-aware live-update polling
* Identical not-found behaviour for inaccessible live-update resources
* UTC timestamp storage

The application follows a deny-by-default approach.

A user should never gain access merely by changing:

* A URL
* An identifier
* A hidden form value
* A JSON request
* JavaScript
* A revision token

## Quick Start

### Clone the Repository

```bash
git clone https://github.com/dhbillson/billsons-tasks.git
cd billsons-tasks
```

### Create the Environment File

```bash
cp .env.example .env
```

Review the generated `.env` and replace development values and secrets before
production use.

---

### Start the Application

```bash
docker compose up -d --build
```

Check container status:

```bash
docker compose ps
```

View application logs:

```bash
docker compose logs -f app
```

---

### Apply Database Migrations

```bash
docker compose exec app alembic upgrade head
```

---

### Initial Application Setup

Seed application settings:

```bash
docker compose exec app python scripts/seed_settings.py
```

Create the initial administrator:

```bash
docker compose exec app python scripts/create_initial_admin.py
```

After this, sign in through the web interface and create the required
companies, users and memberships.

---

## Configuration

Configuration is provided through environment variables.

Start with:

```bash
cp .env.example .env
```

Important settings include application configuration, database access, session
security, timezone configuration and live-update behaviour.

### Live Updates

Polling can be enabled or disabled globally:

```env
LIVE_UPDATES_ENABLED=true
```

The polling interval is configurable:

```env
LIVE_UPDATES_POLL_INTERVAL_SECONDS=5
```

A short interval provides faster visible updates.

A longer interval reduces polling frequency.

Billson's Tasks uses PostgreSQL with Alembic migrations.

```bash
docker compose exec app alembic upgrade head
```

```bash

docker compose exec app \
```

### Roll Back One Migration

```bash
docker compose exec app alembic downgrade -1
```

## Reverse Proxy Support

Billson's Tasks is designed to operate behind a reverse proxy.

Suitable options include:

* Traefik
* Nginx Proxy Manager
* Nginx
* Caddy

HTTPS termination should normally be handled by the reverse proxy.

No special WebSocket configuration is required for live updates because the
current collaboration implementation uses normal HTTP polling.

---

## Backups

The PostgreSQL database should be backed up regularly.

If helper backup scripts are included in the deployment, they should be used
according to the deployment's backup policy.

At minimum, a backup strategy should preserve:

* PostgreSQL data
* Environment configuration
* Reverse proxy configuration where applicable

Database backups should be tested periodically by performing a restore in a
non-production environment.

## Updating

Before updating a production installation:

1. Back up the database.
2. Pull or deploy the new application version.
3. Rebuild or pull the application image.
4. Apply Alembic migrations.
5. Restart the application.
6. Check application logs.
7. Run appropriate health and acceptance checks.

Example source deployment:

```bash
git pull

docker compose down

docker compose build app

docker compose up -d

docker compose exec app alembic upgrade head
```

For deployments using published container images, pull the required image
instead of rebuilding locally.

## Architecture

Billson's Tasks follows a layered application structure.

```text
Web Route
    │
    ▼
Service
    │
    ▼
Repository
    │
    ▼
Database
```

Permission checks are performed before protected business operations.

Repositories are responsible for persistence.

Services are responsible for business rules.

Routes coordinate HTTP behaviour.

Templates and JavaScript provide the user interface but are never relied upon
for security.

---

## Design Principles

Billson's Tasks follows several core principles:

* Self-host first
* Server-side security
* Explicit organisational isolation
* Minimal infrastructure
* Predictable permissions
* Recoverable deletion
* Strong auditability
* Simple deployment
* Human-readable configuration
* Full ownership of application data

The application intentionally avoids adding infrastructure until there is a
clear operational requirement for it.

For example, multi-user live updates currently use lightweight polling rather
than introducing WebSockets, Redis or a message broker.
